# مساعد المهام بالعربية — Node.js + Groq + PostgreSQL

خادم لمهمة مهندس الذكاء الاصطناعي المقدمة. `POST /chat` ينشئ ويحدّث المهام، ويتعامل مع طلبات الموظفين والموافقات، ويجيب من البنود الستة لسياسة الشركة باللغة العربية. البيانات تُحفظ في PostgreSQL ويمكن استضافتها في السحابة. Telegram هو واجهة المحادثة؛ لا يوجد واجهة ويب مطلوبة.

**جميع القواعد الحالية:** [قواعد النظام المعتمدة](docs/business-rules.md). **القدوات ونطاق التسليم:** [capabilities](docs/capabilities.md). **الأدلة ضد معايير التقييم:** [assessment](docs/assessment-report.md).

## التشغيل

### Docker (موصى به)

يتطلب Docker Desktop ومفتاح Groq صالح. قم بتكوين الأسرار دون تعديل الكود المصدري:

```bash
cp -n .env.example .env   # -n: لا تتم الكتابة فوق ملف .env الموجود (قد يحتوي على مفتاحك)
# اضبط GROQ_API_KEY في .env، ثم:
docker compose up -d --build
curl http://localhost:3000/health
docker compose exec server npm run demo
```

هذا يبدأ PostgreSQL، ويهيئ الجداول وستة موظفين افتراضيين، ويشغّل Node.js 22. PostgreSQL مكشوف فقط على localhost:5433، وAPI على localhost:3000. SERVER_PORT و POSTGRES_PORT يمكنهما تغيير منافذ المضيف دون تعديل Compose. Demo ينشئ مهام اختبار؛ استخدم مكدس/قاعدة بيانات تقييم مخصصة.

### بديل Node.js المحلي

يتطلب Node.js 22، PostgreSQL ومفتاح Groq صالح:

```bash
cp -n .env.example .env
# اضبط GROQ_API_KEY و DATABASE_URL في .env.
docker compose up -d db
npm ci
npm start
# في طرفية ثانية:
npm run demo
```

رابط PostgreSQL السحابي يعمل مع نفس الكود. لـ TLS الم_verified اضبط DATABASE_SSL=true؛ اختيارياً اضبط DATABASE_CA_FILE. تجنب معلمات sslmode المتضاربة ولا تعطّل التحقق من الشهادة أبداً. بيانات اعتماد Compose هي افتراضات التقييم المحلي، وليست بيانات اعتماد قاعدة بيانات عامة.

إعدادات AI الافتراضية:

```dotenv
AI_BASE_URL=https://api.groq.com/openai/v1
AI_MODEL=qwen/qwen3.8-27b
GROQ_API_KEY=your-key
```

يستخدم المحول [نقطة نهاية متوافقة مع Groq](https://console.groq.com/docs/openai) و [المخرجات المنظمة](https://console.groq.com/docs/structured-outputs). نماذج Groq المدعومة (بما في ذلك نموذج Qwen المُعد) تستخدم JSON Schema الصارم؛ النماذج المتوافقة الأخرى تستخدم وضع كائن JSON. الخادم يتحقق من الحقول المستخرجة بشكل منفصل في كلا الوضعين. يمكنك تغيير الرابط الأساسي والنموذج، باستخدام `AI_API_KEY` لموفر آخر متوافق؛ امسح `GROQ_API_KEY` أولاً لأنه له الأولوية. لا يتم استخدام موفر احتياط أو محلل نواة غير متصل بشكل صامت.

## API

```bash
curl http://localhost:3000/chat \
  -H 'Content-Type: application/json' \
  -d '{"user_id":2,"message":"سجّل مهمة لخالد بكرة الساعة 10 يراجع عرض السعر"}'
```

شكل الاستجابة (المعرفات والتواريخ تعتمد على قاعدة البيانات واليوم الحالي):

```json
{
  "action": "create_task",
  "action_type": "execution",
  "task_id": 1,
  "task": { "id": 1, "assignee_id": 4, "description": "يراجع عرض السعر", "due_at": "2026-10-15T07:00:00.000Z" },
  "rescheduled": false,
  "message": "تم تسجيل المهمة لخالد بتاريخ 2026-10-15 الساعة 10:00."
}
```

تتضمن الإجراءات `create_task`، `list_tasks`، `policy_answer`، `create_request`، `list_requests`، `list_approvals`، `list_reports`، `decide_request`، `submit_report`، `update_task`، `edit_task`، `view_report`، `review_report`، و `list_audit`؛ الإجراءات غير المعروفة تستخدم `unknown`. كل استجابة JSON تتضمن `action`، `action_type`، `message` و `reply` (مطابقة لـ `message`، محفوظة لعقد R1 في المهمة). النتائج هي `execution`، `rejection`، `postpone`، `inquiry`، و `exception`. تحذف API `response_type` الداخلي وبيانات الطلب. `/chat` يقبل `prompt` أو `message` الموجود، مع `user_id` عدد صحيح موجب يطابق هوية الحامل. `GET /health` يتحقق من PostgreSQL. الطلبات محدودة بـ 16 KiB، الرسائل بـ 4000 حرف، وطلبات AI بـ 20 ثانية. راجع [عقد التكامل](docs/integration-contract.md) للتحقق من Telegram، الجلسات و CI/CD.

## الهوية والصلاحيات

`AUTH_MODE=demo` يطبق عقد `user_id` المقدم من المتصل في المهمة وهو للتقييم المحلي. عند النشر العام، استخدم `AUTH_MODE=token` وقم بتعيين أسرار عشوائية فريدة بطول 32 حرف على الأقل لمعرفات الموظفين:

```dotenv
AUTH_MODE=token
AUTH_TOKENS_JSON={"2":"replace-with-a-unique-random-secret-of-at-least-32-characters"}
```

أرسل `Authorization: Bearer <employee-token>`. يجب أن يطابق `user_id` تلك الهوية. أنشئ الرموز باستخدام `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. احفظ المفاتيح/الرموز فقط في `.env` أو أسرار السحابة، أبداً في Git. لنظام موظف حقيقي، استبدل هذا التعيين للرموز بموضوع JWT المVerified من مزود الهوية الخاص بك.

يتم تحميل الأدوار من PostgreSQL، أبداً من الرسائل أو مخرجات النموذج:

- الموظفون ينشئون/يقرؤون مهامهم الخاصة.
- المشرفون ينشئون/يقرؤون المهام داخل قسمهم.
- المديرون ينشئون/يقرؤون المهام للجميع.

`src/chat.js` يتحقق من الطلبات و `src/store.js` يتحقق مرة أخرى على حدود قاعدة البيانات. إنشاء المهمة وإدخال التدقيق الخاص بها يشاركان معاملة. القرارات المحدودة تستعلم فقط الصفوف المصرح بها. يتلقى النموذج أسماء الموظفين وبنود السياسة، أبداً محتويات المهام الموجودة، الأدوار، بيانات الاعتماد أو الوصول لقاعدة البيانات. إدخالات التدقيق تحذف رسائل الدردشة الخام.

## التواريخ والسياسة

يحل الخادم التواريخ في `Asia/Riyadh`، ويخزن الطوابع الزمنية كـ PostgreSQL `TIMESTAMPTZ`، ويعرض وقت الرياض. `بكرة`، `بعد بكرة`، أيام الأسبوع القادمة والتواريخ ISO مدعومة. يعني يوم الأسبوع حدوثه القادم الصارم بعد اليوم، بما في ذلك "الجاي". الساعات غير المؤهلة 1–7 تستخدم سياق العمل بعد الظهر/المساء (13:00–19:00)؛ 8–11 تعني الصباح و 12 تعني الظهر. الفترات الصريحة والساعات المملوءة بأصفار مثل 03:00 محترمة. "العصر" وحده يعني 16:00؛ "1 الظهر" يعني 13:00. التفاصيل المفقودة أو الغامضة تؤدي إلى طلب توضيح. مهام الجمعة تنتقل إلى السبت في نفس الساعة. مواعيد المهام قد تكون خارج ساعات عمل الشركة، بما في ذلك بعد الظهر يوم السبت. الجمعة لا تزال تنتقل إلى السبت في نفس الساعة. تحديثات الحالة مسموحة يومياً قبل موعد المهمة أو بعده وفي الأيام التالية، ولكن قبل نهاية دوام يوم التحديث: 16:00 من الأحد للخميس و12:00 السبت؛ الجمعة عطلة. ساعة الخادم هي المرجع. المواعيد الجديدة وتعديلات الجدول لا يمكن أن تكون أبكر من وقت الخادم.

Groq يستخرج نية ويختار معرفات بنود السياسة. التطبيق يرجع بنود المصدر المختارة بالضبط؛ لا يستخدم إجابات سياسة مُنشأة بحرية. المعلومات غير المعروفة تُرجع "هذه المعلومة غير متوفرة في نص سياسة الشركة." تعتمد الصلة على تصنيف النموذج ويتم التحقق منها في العرض الحي. يجب تمييز التفاصيل غير المدعومة كغير معروفة في موجه الاستخراج.

## إعادة التعيين وطلبات الاختبار العشرة

```bash
npm run db:reset                                  # Docker: docker compose exec server npm run db:reset
bash scripts/test-requests.sh                     # يُشغّل T01–T10 بالترتيب، أو انسخ كتلة curl واحدة في كل مرة
```

`db:reset` يمسح جميع المهام والطلبات وإدخالات التدقيق وبيانات Telegram، ويعيد تشغيل المعرفات من 1 ويعيد زراعة الموظفين الستة الافتراضيين. يرفض التشغيل ما لم يُشير `DATABASE_URL` إلى localhost، 127.0.0.1 أو خدمة `db` في Compose، لذلك لا يمكنه مسح قاعدة بيانات سحابية. `scripts/test-requests.sh` يحتوي على الرسائل العشرة كأوامر `curl` جاهزة للنسخ مع السلوك المتوقع في تعليقات عربية. السرد العربي لفيديو 3–5 دقائق في [docs/video-script-ar.md](docs/video-script-ar.md).

يمكنك أيضاً استخدام Postman لاختبار API. راجع [دليل إعداد Postman](POSTMAN_SETUP.md) للتعليمات والمجموعات الجاهزة للاختبار.

## التحقق والعرض

التغطية الآلية تتضمن صلاحيات PostgreSQL، جميع إجابات السياسة الستة، حدود ساعات العمل، توجيه الطلبات، موافقات المشرف/المدير، مواعيد التقارير الطبية، تحديثات الحالة، موافقات العمل عن بعد المتزامنة وإعادة محاولات Telegram. راجع [سير عمل الطلبات](docs/workflows.md) للأوامر وافتراضات السياسة.

```bash
npm test
npm run demo

# بديل Docker فقط؛ لا حاجة لـ Node.js على المضيف للعرض الحي:
docker compose exec server npm run demo
```

الاختبارات تستخدم محاكي PostgreSQL ونتائج AI افتراضية افتراضياً؛ تغطي جميع السيناريوهات العشرة المقدمة بالترتيب، حل التاريخ، صلاحيات SQL، حقن دور الموجه، مصادقة HTTP وفشل الموفر. لا تُثبت **دقة النموذج الحية**. `npm run demo` يرسل الرسائل العربية العشرة الفعلية للخادم المشغّل ويستدعي Groq بمفتاحك. ينشئ مهام عرض حقيقية في كل تشغيل؛ استخدم قاعدة بيانات تقييم منفصلة.

لاختبارات سير عمل PostgreSQL/Telegram الحقيقية، أنشئ قاعدة بيانات `assistant_test` مؤقتة وشغّل:

```bash
WORKFLOW_TEST_DATABASE_URL=postgresql://assistant:assistant@localhost:5433/assistant_test \
TELEGRAM_TEST_DATABASE_URL=postgresql://assistant:assistant@localhost:5433/assistant_test npm test
```

هذه الاختبارات تنشئ/تحذف مخططات مؤقتة معزولة. اختبارات `TEST_DATABASE_URL` القديمة الاختيارية تحذف جداول التطبيق: لا تشير أبداً لأي إعداد اختبار للإنتاج.

راجع [صفحة القرارات بالعربية — ملف التسليم 03](docs/03-decisions-ar.md) و [قرارات التصميم التفصيلية](docs/decisions.md) للافتراضات، حساب التكلفة والخطوات التالية. المهمة تتطلب فيديو توضيحي 3–5 دقائق بصوتك الخاص، الذي يجب عليك تسجيله بنفسك؛ `npm run demo` يوفر جولة بالرسائل العشرة.

## النشر على Vercel و Neon

راجع [تعليمات النشر](docs/deployment.md). مسارات السحابة تستخدم نفس تطبيق الدردشة والتفويض مثل الخادم المحلي. عمليات نشر Vercel تتطلب وضع الرمز، وتهيئة مخطط Neon تعمل مرة واحدة قبل تقديم الخدمة.

## حدود الموفر والتكلفة

تُرجع حدود معدل Groq HTTP 429 مع Retry-After قبل أي كتابة أعمال. العرض الحي ينتظر ويعيد محاولة هذه الاستجابات حتى ثلاث مرات، لكن لا يعيد محاولة الطفرات الناجحة أو الفشول غير المعروفة. الحصة المحدودة تظل حداً خارجياً. اختياريًا `AI_USAGE_LOG=true` يكتب فقط أعداد الرموز المدخلة/المخرجة الرقمية؛ لا تُسجل أي رسالة أو هوية أو مفتاح. راجع [قرارات التكلفة والتصميم](docs/decisions.md) للمعدلات المذكورة الحالية، الأحجام المقاسة/المفترضة، بدلات الاستضافة وخطة أسبوع إضافي.

### إسناد مهمة لأكثر من موظف

مثال: «سجل مهمة لفهد وخالد بكرة الساعة 10 مراجعة التقرير». يُنشئ مهام مستقلة بنفس الوصف والموعد ويعيدها في `tasks` مع اسم المسند إليه ورقم المهمة. تُراجع صلاحيات جميع الموظفين، وتُحفظ المجموعة وسجل العمليات والإشعارات في معاملة واحدة؛ لا تسجيل جزئي عند الرفض أو نقص اسم.

«أريد عمل مهمة لكل الموظفين لحضور اجتماع بعد غد الساعة ١» مدعومة كذلك: المدير يسند لجميع المسجلين، والمشرف لقسمه، والموظف لا يملك الإسناد الجماعي. موعد الجمعة يُرحّل للسبت بنفس الساعة.
